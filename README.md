# CRM «Omuz» — бэкенд

Серверная часть CRM обучающего центра «Omuz» (Таджикистан): студенты, группы, менторы,
успеваемость, финансы и маркетинг.

Требования — [`TZ_CRM_Omuz_FINAL.md`](./TZ_CRM_Omuz_FINAL.md), план работ — [`ROADMAP.md`](./ROADMAP.md),
история разработки — [`sessions/`](./sessions).

## Стек

TypeScript · NestJS · PostgreSQL · Prisma · Redis + BullMQ · JWT + Passport · argon2id ·
Swagger/OpenAPI · Pino · Docker · Jest + supertest.

Архитектура — модульный монолит. Поток запроса: `Controller → Service → Repository (Prisma) → PostgreSQL`.

## Быстрый старт

### Вариант 1 — Docker (поднимает всё)

```bash
cp .env.example .env

```

Поднимаются `postgres`, `redis` и `app`; миграции применяются автоматически
(`prisma migrate deploy`) перед стартом приложения.

## Конвенции API

Базовый префикс — `/api/v1` (служебный `/health` вынесен из префикса).

**Успешный ответ:**

```json
{ "data": { "id": "..." } }
```

**Список (постраничный):**

```json
{
  "data": [],
  "meta": { "total": 137, "page": 1, "limit": 20, "totalPages": 7 }
}
```

Query-параметры списков: `page` (с 1), `limit` (по умолчанию 20, максимум 100),
`search`, `sort`, `order` (`asc`/`desc`) + доменные фильтры.

**Ошибка:**

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Ошибка валидации входных данных",
    "details": ["phone must be a valid phone number"],
    "requestId": "9f1c…",
    "timestamp": "2026-07-26T10:15:00.000Z"
  }
}
```

Коды: `VALIDATION_ERROR` (400), `UNAUTHORIZED` (401), `FORBIDDEN` (403), `NOT_FOUND` (404),
`CONFLICT` (409), `UNPROCESSABLE_ENTITY` (422), `TOO_MANY_REQUESTS` (429), `INTERNAL_ERROR` (500).

`requestId` совпадает с заголовком `x-request-id` и с полем `req.id` в логах — по нему
запрос ищется в Pino-логах.

## Аутентификация

Заголовок `Authorization: Bearer <access>`. Access живёт 1 час, refresh — 2 недели.

**Закрыто по умолчанию:** `JwtAuthGuard` зарегистрирован глобально, поэтому новый эндпоинт
защищён сразу; открыть его можно только явно — декоратором `@Public()`.

| Эндпоинт | Назначение |
|---|---|
| `POST /api/v1/auth/register` | Регистрация студента (телефон — логин, пароль ≥8) |
| `POST /api/v1/auth/login` | Вход по номеру телефона и паролю |
| `POST /api/v1/auth/refresh` | Новая пара токенов; предъявленный refresh инвалидируется |
| `POST /api/v1/auth/logout` | Выход с текущего устройства |
| `POST /api/v1/auth/logout-all` | Выход со всех устройств |
| `POST /api/v1/auth/password/forgot` | Запрос 6-значного кода восстановления на email |
| `POST /api/v1/auth/password/reset` | Смена пароля по коду |

Как это устроено:

- пароли — **argon2id** (64 МиБ, 3 прохода); телефоны нормализуются в **E.164**,
  поэтому `901234567`, `992901234567` и `+992 (90) 123-45-67` — один и тот же логин;
- **серверные сессии**: строка `sessions` = одно устройство. В БД лежит только SHA-256
  от refresh-токена, сам токен не хранится;
- **ротация**: каждый обмен выдаёт новый refresh и заменяет отпечаток в сессии. Если
  предъявлен уже заменённый токен, сессия гасится целиком — так отрабатывается кража токена;
- вход отвечает одинаково на неизвестный номер и неверный пароль (и тратит одинаковое время),
  чтобы форму входа нельзя было использовать как проверку, кто зарегистрирован.

### Сброс пароля

Код из 6 цифр живёт 10 минут; не более **3 запросов кода в час** и **3 попыток ввода** на код —
на исчерпании код гасится досрочно. Смена пароля отзывает все сессии аккаунта.

- `password/forgot` отвечает одним и тем же текстом независимо от того, существует аккаунт
  или нет; заблокированному аккаунту код не отправляется — сброс не должен обходить блокировку;
- код хранится как **HMAC-SHA256 с `PASSWORD_RESET_SECRET`**, а не как argon2-хеш:
  6 цифр — это 10⁶ вариантов, быстрый хеш из утёкшего дампа обращается мгновенно, а медленный
  превратил бы публичный `password/forgot` в дорогую операцию (вектор DoS). Секрета нет в БД,
  поэтому перебор дампа бесполезен, а онлайн-перебор ограничен счётчиком попыток;
- письмо уходит через абстракцию `MailerService` на языке аккаунта (ru/en/tg).
  **Реальный провайдер пока не подключён:** `LogMailerService` пишет письмо в лог на уровне
  `debug` (для разработки задайте `LOG_LEVEL=debug`). Провайдер появится в Фазе 11.

### Перевод Студент → Сотрудник

`POST /api/v1/students/{id}/promote-to-employee` — выпускник становится сотрудником (ТЗ 3.1).
Всё выполняется одной транзакцией:

- **логин не меняется** — аккаунт не пересоздаётся: `phone`, `email` и хеш пароля прежние,
  меняется только `type` на `EMPLOYEE`;
- **учебная история сохраняется** — строка `students` не удаляется и не копируется; журнал,
  баллы и коины (Фаза 5) продолжают ссылаться на тот же профиль. Сотрудник хранит ссылку
  на него в `formerStudentId`;
- **профиль один** — аккаунт отвязывается от студента и привязывается к сотруднику
  (ТЗ 3.1: Student **или** Employee, не одновременно);
- **сессии гасятся** — тип аккаунта зашит в access-токен, а стратегия не ходит в БД на каждый
  запрос; без гашения бывший студент до часа ходил бы с токеном типа `STUDENT`;
- студента **без аккаунта** тоже можно перевести (ТЗ 5.3: аккаунт опционален) — тогда
  создаётся только профиль сотрудника.

Статус студента при переводе не меняется: человек может продолжать учиться на другом курсе,
оставаясь ментором.

Доступ: `@RequireAccountType(AccountType.EMPLOYEE)` плюс право `Permission.Students.Promote`.

## Права доступа (RBAC)

Сотрудник имеет одну или несколько **позиций**; его права — **объединение** прав всех
позиций (ТЗ 3.2). У студента позиций нет: ему доступен только просмотр своих данных.

Позиция — она же «роль» из экрана Administration → Users. ТЗ разводит термины `Role`
и `Position`, но сущность одна: права выдаются только позициями, и вторая таблица
создала бы второй источник прав, в который пришлось бы заглядывать при каждом
разборе «почему у него нет доступа».

**Каталог прав** — в нотации `Permission.<Раздел>.<Действие>` (`Permission.Mentors.Views`).
Источник истины — код (`src/rbac/permission-catalog.ts`), а не таблица:

```ts
@RequirePermission('Permission.Students.Promote')
promoteToEmployee() {}
```

Тип кода выводится из каталога, поэтому опечатка **не компилируется**. Если бы каталог
жил только в БД, опечатка означала бы право, которого нет ни у кого, — эндпоинт молча
стал бы недоступен всем. В таблице `permissions` хранятся описание и переключатель
`isEnabled` (ТЗ 5.15); при старте приложения таблица приводится к каталогу
(`PermissionCatalogSyncService`): новые коды добавляются, исчезнувшие — **не удаляются**
(вместе с ними каскадом ушли бы выданные позициям галочки), а просто перестают действовать.

Детали:

- декоратор `@RequirePermission(...)` сам навешивает `PermissionsGuard` — забыть
  `@UseGuards` и оставить эндпоинт открытым нельзя;
- при перечислении нескольких кодов требуются **все**;
- права **не кладутся в токен**: он живёт час, и снятая позиция действовала бы ещё час.
  Набор читается из БД на каждый защищённый запрос, поэтому отзыв срабатывает сразу;
- позиция **Director** системная: она существует всегда и держит весь каталог прав —
  иначе после каждой фазы, добавляющей права, у руководителя не хватало бы доступа
  к новому разделу, а выдать его было бы некому.

Стартовый справочник позиций (`Director`, `Admin`, `Manager`, `Mentor`, `Developer`)
заводится миграцией один раз; дальше им управляет администратор.

### Первый запуск: кем войти

На пустой базе система закрыта сама на себя: регистрация создаёт только студентов,
перевод в сотрудники требует права, назначение ролей — тоже. Первого руководителя
заводит скрипт:

```bash
npm run seed:admin -- --phone=+992901234567 --email=director@omuz.tj \
                      --first-name=Фаррух --last-name=Раҳимов
```

Пароль можно не указывать — скрипт сгенерирует его и покажет **один раз**
(так он не осядет в истории команд). Значения читаются и из переменных окружения
`SEED_ADMIN_PHONE`, `SEED_ADMIN_EMAIL`, `SEED_ADMIN_FIRST_NAME`, `SEED_ADMIN_LAST_NAME`,
`SEED_ADMIN_MIDDLE_NAME`, `SEED_ADMIN_PASSWORD`.

Скрипт создаёт аккаунт сотрудника, профиль и назначение позиции `Director` **одной
транзакцией**; повторный запуск безопасен — существующий аккаунт не меняется
(пароль в том числе), скрипт лишь досогласовывает позицию. Телефон, занятый аккаунтом
студента, он не перехватывает.

Это скрипт, а не эндпоинт первичной настройки: публичный путь к правам `Director`
пришлось бы охранять, и он остался бы в приложении навсегда ради одного применения.

- **филиал с привязанными записями не удаляется** (409): аудитории, группы, студенты
  и сотрудники ссылаются на него `RESTRICT`. Чтобы вывести филиал из работы, не теряя
  историю, — статус `INACTIVE`. Так же **не удаляется курс, по которому набраны группы**,
  и **группа, в составе которой есть студенты**;
- названия филиала и курса уникальны **без учёта регистра**; названия аудитории и группы —
  уникальны **внутри филиала** («101» и «Frontend-1» могут быть в каждом);
- несуществующий `branchId` или `courseId` в теле запроса — **422**, а не 404: ресурс из пути
  найден, не найдено то, что пришло в теле (тот же выбор, что в назначении ролей);
- аудиторию и группу можно перенести в другой филиал — тёзка проверяется в филиале
  назначения; группу можно ещё и перевести на другой курс;
- `fee` курса хранится как `DECIMAL(12,2)` (сомони) и отдаётся числом; цвета — `#RRGGBB`;
  длительность — пара «число + единица» (`DAY`/`WEEK`/`MONTH`);
- `isLastCourse` — «Is last course» из ТЗ 5.6: по нему в Фазе 7 сработает автовыпуск.
  Флаг курса отдаётся и в карточке группы — видно, какая группа его запустит;
- у группы статусы `RECRUITING` (набор) · `ACTIVE` (идёт) · `FINISHED` (завершена) ·
  `CANCELLED` (не состоялась); порядок переходов не ограничен;
- даты группы — календарные (`YYYY-MM-DD`, без времени и часового пояса); дата окончания
  раньше даты начала — 400; `durationUnit` без `durationValue` — тоже 400;
- пустая строка в необязательном поле `PUT` **очищает** его (включая даты), а не переданное
  поле остаётся прежним.

### Менторы группы (ТЗ 5.5)

У группы их несколько, у каждого своя роль: `TEACHING` (ведёт занятия) или `SUPPORT`
(помогает на них). Маршруты вложены в группу — назначение не существует отдельно от неё.

- **отдельной позиции «Mentor» не требуется**: правило пришлось бы опирать на *название*
  позиции, а его администратор меняет через `/positions` (`Mentor`, в отличие от `Director`,
  не помечена `isSystem`) — переименование молча сломало бы назначение менторов. Заодно
  руководитель, который сам ведёт занятия, не попадал бы под правило;
- **сотрудник, выведенный из штата (`INACTIVE`), ментором не назначается** — 422; но уже
  назначенный остаётся в группе: история не переписывается задним числом;
- **один сотрудник в группе ровно один раз** (409 на повторное назначение): две роли
  одновременно означали бы, что часы занятия посчитаны дважды при расчёте зарплаты (ТЗ 5.16).
  Роль меняется через `PUT`, а не вторым назначением;
- **несуществующий `employeeId` — 422**, а не 404: он пришёл в теле, а не в пути. Неизвестная
  группа в пути — 404, и это сообщение отличимо от «ментор не назначен на эту группу»;
- **снятие ментора удаляет только назначение**, профиль сотрудника не трогается. Удаление
  группы или сотрудника уносит назначения каскадом: это связь, а не запись со своей историей;
- `PUT` (смена роли) в перечне маршрутов ТЗ 5.5 нет — добавлен, потому что иначе перевод
  Support → Teaching делался бы снятием и повторным назначением, а между двумя запросами
  у группы нет преподавателя.

### Расписание группы (ТЗ 5.5, 5.10)

Слот — это **повторяющееся еженедельно** занятие: «понедельник 10:00–12:00, аудитория 101».
Одна строка описывает весь курс, а календарь Day/Week/Month (`GET /timetable`, Фаза 10)
разворачивает слоты в конкретные даты на лету.

- **время приходит и отдаётся как `HH:MM`**, а в БД лежит минутами от полуночи: целое число
  сравнимо и сортируемо без разбора часовых поясов. Окончание не позже начала — 400;
- **аудитория — только из филиала группы** (422): комната физически стоит в своём филиале.
  Аудитория необязательна — у занятий онлайн её нет;
- **ментор — только из числа менторов группы** (422, `/groups/{id}/mentors`): иначе «менторы
  группы» и «кто ведёт занятия» разошлись бы, а по вторым считаются часы (ТЗ 5.16);
- **занятия не пересекаются** — 409 по трём причинам: у самой группы, в одной аудитории
  и у одного ментора. Занятия «встык» (12:00–14:00 после 10:00–12:00) конфликтом не считаются;
- пересечение считается только для групп, чьи **сроки обучения идут внахлёст** и которые
  не в статусе `FINISHED`/`CANCELLED`: курс длится около месяца, группы в одной аудитории
  сменяют друг друга, и без этого расписание нового набора упиралось бы в прошлогоднее;
- **аудиторию, в которой стоят занятия, удалить нельзя** (409) — как филиал с записями;
- **группу с занятиями в аудиториях нельзя перенести в другой филиал** (422): комнаты вместе
  с ней не переезжают, а молча снять аудитории значило бы потерять места проведения;
- **снятие ментора с группы убирает его из её занятий** одной транзакцией; сколько занятий
  осталось без ведущего, возвращается в ответе `DELETE /groups/{id}/mentors/{employeeId}`;
- пустая строка в `roomId`/`mentorId` при `PUT` **убирает** аудиторию или ментора из занятия;
- **типа занятия (Lecture/Practice/Exam) у слота нет**: при еженедельном повторении каждый
  понедельник — это другой день программы, и тип берётся из силлабуса, а не из слота.

### Состав группы (ТЗ 5.5, 5.12)

Членство студента в группе — отдельная запись со своим статусом: `ACTIVE` (учится),
`LEFT` (покинул курс), `FINISHED` (завершил), `TRANSFERRED` (переведён в другую группу).
Эта же строка играет роль `Enrollment` из ТЗ 4: закрытые членства не удаляются, а остаются
с причиной и датой — из них и складывается «Left courses» (ТЗ 5.12).

- **статус членства ≠ `Student.status`** (ТЗ 5.3), но не независим от него: студент может
  параллельно учиться на другом курсе, и уход из одной группы не делает его неактивным
  в центре. После каждого изменения состава статус профиля **пересчитывается** из всех
  членств студента — правило описано в разделе «Статус студента и его членства»;
- **одно действующее членство на курс** (409): учиться на Frontend и English параллельно
  можно, в двух группах одного курса — нет. Закрытые членства не мешают: ушедший из
  «Frontend-1» спокойно зачисляется в «Frontend-2»;
- **зачисление идёт пачкой и одной транзакцией**: группа с половиной набора хуже, чем отказ
  целиком. Несуществующий студент — 422 с перечислением **только недостающих**, уже
  зачисленный — 409 с именем;
- **вернувшийся в группу занимает прежнюю строку**: причина и дата прошлого ухода снимаются,
  второго членства в той же группе не заводится (составной первичный ключ);
- **причина (Reason) обязательна** при любой смене статуса, включая возврат в обучение:
  «почему студент снова активен» нужно знать так же, как «почему ушёл»;
- **`TRANSFERRED` не ставится сменой статуса** (422) — только переводом: иначе студент
  оказался бы «переведён» в никуда. Перевод закрывает членство в прежней группе и заводит
  действующее в новой одной транзакцией, сохраняя ссылку «откуда пришёл»;
- **перевод на соседний курс разрешён** — правило «одна группа на курс» проверяется у группы
  назначения. Перевод в ту же группу — 422;
- **исключение из состава (`DELETE`) удаляет членство вместе с историей** — оно для
  зачисленных по ошибке. Настоящий уход оформляется статусом `LEFT`, чтобы остаться
  в отчёте по покинувшим курс;
- **набор сверх `capacity` не запрещён**: «Required students» из ТЗ 5.5 — плановая цифра
  для показа «набрано/вместимость» (`enrolledCount`/`capacity` в карточке группы), а не предел.

#### Выгрузка и импорт состава (ТЗ 5.5: Import/Export)

```http
GET  /api/v1/groups/{groupId}/students/export?status=LEFT
POST /api/v1/groups/{groupId}/students/import     { "csv": "Телефон\n+992901234567" }
```

- **выгрузка отдаёт файл, а не `{ data }`** — единственное исключение из общего формата
  ответа (ТЗ 3.5), сделанное явным декоратором `@RawResponse()`: `text/csv; charset=utf-8`
  с **BOM** (без него Excel под Windows читает UTF-8 как cp1251) и `Content-Disposition`
  с именем файла в двух видах (ASCII и `filename*` с названием группы);
- **выгружается весь отобранный состав**, а не страница; доменные фильтры остаются, поэтому
  `?status=LEFT` даёт секцию «Left course» отдельным файлом. Порядок фиксированный
  («фамилия, имя»), потолок — 5000 строк;
- **импорт только зачисляет уже заведённых студентов**: связь ищется по телефону
  (`Student.phone` уникален), профили не создаются — это карточка студента из ТЗ 5.3
  со своей валидацией всех полей, и заводить людей боком через CSV не стоит;
- **файл передаётся текстом в JSON-теле** (`{ "csv": "…" }`), без `multipart/form-data`:
  приём файлов — отдельный сквозной кусок инфраструктуры, который проект пока не заводил
  (материалы уроков — тоже ссылки, а не загрузки);
- **колонка телефона ищется по названию** (`Телефон`, `phone`, `номер`), остальные колонки
  игнорируются — поэтому **файл собственной выгрузки принимается обратно без правки**;
- принимаются оба разделителя (`,` и `;` — второй ставит Excel в русской локали), BOM,
  кавычки с удвоением и оба вида переводов строк; номера нормализуются в E.164 теми же
  правилами, что и везде (`901234567` → `+992901234567`);
- **файл применяется целиком или не применяется вовсе**: любая плохая строка — 422
  со списком `{ line, phone, reason }` (номера строк — как в файле; перечисляются первые 50,
  общее число ошибок отдаётся рядом). Проверяются пустой и неразобранный телефон, повтор
  в файле, отсутствие профиля, «уже учится в этой группе» и «уже учится в другой группе
  этого курса»;
- потолки: 200 КБ на файл и 500 строк данных.

### Студенты (ТЗ 5.3)

`GET/POST /api/v1/students`, `GET/PUT/DELETE /api/v1/students/{id}` — админ-сторона:
список с фильтрами, карточка и форма (пол, статус, доп. телефоны, филиал, Telegram,
заметки, фото).

- **профиль заводится без аккаунта**: ТЗ 5.3 называет логин опциональным и выдаёт его
  отдельным действием «Invite». `account` в карточке — `null`, пока приглашения не было,
  а фильтр `?hasAccount=false` даёт список тех, кого стоит пригласить;
- **телефон уникален среди студентов** (409 с именем того, за кем он записан) и
  нормализуется в E.164 — конфликт ловится и на номере, записанном в другом формате.
  Контактный телефон профиля и логин аккаунта — **разные поля** (решение сессии 0002);
- **доп. телефоны** приводятся к E.164 по одному, повторы отбрасываются молча (тот же
  номер в двух записях — опечатка, а не повод отказывать), пустой массив очищает список;
- **фильтры ТЗ 5.3**: `status`, `groupId` («Group»), `courseId` («Course»), плюс `branchId`
  (ТЗ 3.3) и `hasAccount`; поиск `search` — по имени, фамилии, телефону и email.
  Фильтры по группе и курсу смотрят **только на действующие членства**: «студенты группы» —
  это те, кто в ней учится, а не все, кто когда-либо в ней числился;
- **несуществующий филиал в теле — 422** (ресурс из пути найден, не найдено то, что пришло
  в теле), пустая строка в `branchId` снимает привязку;
- **удаляется только «чистый» профиль**: студент с членствами в группах — 409 с их числом,
  переведённый в сотрудники — 409. Вместе со строкой студента исчезли бы причины и даты
  ухода из групп (ТЗ 5.12), а позже баллы и коины. Для «человек больше не учится» есть
  статусы `NO_ACTIVE` и `BLOCK` (ТЗ 5.3: Block ≠ Delete);
- **аккаунт удаляется вместе с профилем** — логина без профиля ТЗ 3.1 не допускает.

#### Статус студента и его членства

Статусы профиля — `ACTIVE` / `NO_ACTIVE` / `FINISHED` / `BLOCK` (ТЗ 5.3). Их можно
поставить руками через `PUT`, но после **любого** изменения состава группы статус
пересчитывается из всех членств студента:

- есть действующее членство → `ACTIVE`;
- действующих нет → смотрится **последнее по времени** закрытое: `FINISHED` → `FINISHED`,
  `LEFT`/`TRANSFERRED` → `NO_ACTIVE`;
- `BLOCK` автоматика **не перебивает** — это запрет входа, а не факт учёбы;
- профиль без единого членства правило не трогает — им управляет оператор.

Почему по последнему событию, а не по приоритету статусов: статус профиля отвечает на вопрос
«что с человеком сейчас». По приоритету «FINISHED важнее» выпускник, бросивший второй курс,
навсегда остался бы выпускником и не попал бы в отчёт по оттоку (ТЗ 5.12: Left courses —
это студенты со статусом No Active); по обратному приоритету выпускник трёх курсов числился
бы покинувшим из-за одного давнего ухода.

**`BLOCK` через `PUT` не ставится и не снимается — 422.** По ТЗ 5.3 «Block» это блок
**входа**, то есть статус профиля и `Account.status` вместе. Поставленный формой, он
пометил бы студента заблокированным, оставив ему возможность войти; снятый формой —
наоборот, вернул бы «активный» статус человеку, которому вход по-прежнему закрыт.
Оба состояния выглядят рабочими и расходятся молча, поэтому для них есть отдельное
действие.

#### Приглашение и блокировка (ТЗ 5.3: Invite / Block)

```http
POST /api/v1/students/{id}/invite    { "email": "nigina@mail.tj", "locale": "RU" }
POST /api/v1/students/{id}/block     { "blocked": true }
```

**Invite** — выдача логина заведённому профилю:

- **логином становится контактный телефон карточки** (ТЗ 3.1), задать его отдельно нечем;
- **пароль система не придумывает**: аккаунт закрывается непригодным случайным секретом,
  которого не знает никто, а студенту уходит письмо с одноразовым кодом (6 цифр, ~10 минут).
  Пароль он задаёт сам общим путём `POST /auth/password/reset` — тем же, что и при забытом
  пароле. Пароль не проходит ни через руки сотрудника, ни через историю запросов;
- **почта обязательна**: без неё приглашение отправить нечем — 422. Адрес берётся
  из карточки, а переданный в теле заодно записывается в неё, чтобы логин и профиль
  не разошлись;
- **повторное приглашение — 409**: логин уже есть, а забытый пароль восстанавливается
  публичным `POST /auth/password/forgot`;
- занятый телефон или email — 409 с указанием, что именно занято; заблокированный
  студент — 422 (свежий активный аккаунт снял бы блокировку сам).

**Block** — обратимое закрытие входа:

- одной транзакцией ставит `Student.status = BLOCK` **и** `Account.status = BLOCKED`,
  живые сессии гасит: обновить токены заблокированный больше не сможет. Выданный ранее
  access-токен доживёт свой час — стратегия намеренно не ходит в БД (решение сессии 0002);
- **`blocked: false` возвращает доступ** и восстанавливает статус профиля по членствам:
  учится → `ACTIVE`, прошёл курс → `FINISHED`, ушёл → `NO_ACTIVE`. Статус до блокировки
  нигде не хранится (ТЗ такого поля не просит), поэтому выводится заново; профиль без
  учебной истории возвращается в `ACTIVE` — значение нового профиля;
- **студент без логина блокируется тоже** — блокируется профиль.

#### Обратная связь (ТЗ 5.3: Feedback)

`GET/POST /api/v1/students/{studentId}/feedback`, `DELETE …/feedback/{feedbackId}` —
заметки сотрудников о студенте: наблюдение ментора, разговор с родителями, причина пропусков.

- **автор берётся из токена**, а не из тела: подписаться чужим именем нельзя даже по ошибке.
  Уход сотрудника заметку не уносит — `author` становится `null` (она про студента);
- **оценки в заметке нет**: успеваемость и рейтинг считаются по журналу (ТЗ 5.8, 5.13),
  и вторая числовая шкала конкурировала бы с ними;
- **правки нет, только добавление и удаление**: исправленное задним числом наблюдение
  перестаёт быть тем, что видел автор. `DELETE` добавлен сверх перечня маршрутов ТЗ —
  иначе ошибочную заметку нельзя было бы убрать;
- лента постраничная, **свежие сверху**; фильтр `authorId`, поиск `search` по тексту;
- просмотр закрыт `Permission.Students.Views`, запись и удаление — `Permission.Students.Feedback`.

#### Родители и опекуны (ТЗ 4: Parent/Guardian)

`GET/POST /api/v1/students/{studentId}/parents`, `PUT/DELETE …/parents/{parentId}` —
контакты родителей. Маршрутов ТЗ для них не перечисляет, границы задаёт раздел
`Permission.Parents.*` из каталога прав.

- **запись родителя общая, а не принадлежит студенту**: у одного человека бывает несколько
  детей в центре. Копия его контактов разошлась бы с оригиналом на первой же смене номера,
  а обзвон родителей группы посчитал бы его дважды;
- **родитель узнаётся по телефону**: если номер уже в системе, `POST` не заводит вторую
  запись, а привязывает существующую — в ответе `created: false` и `childrenCount` больше
  единицы. Отдельного справочника `/parents` нет: номер оператор вводит и так, а второй
  экран стоил бы ему лишнего запроса. Повтор у **того же** студента — 409;
- **пустые поля существующей записи дозаполняются** данными из запроса, заполненные —
  **не перезаписываются**: иначе, добавляя родителя своему студенту, оператор молча
  правил бы карточку чужого. Осознанная правка делается через `PUT`, где она видна
  (`childrenCount` в ответе показывает, скольких детей она затронет);
- **степень родства (`relation`) живёт на связке**, а не в записи: один человек бывает
  матерью одному ребёнку и опекуном другому. Она необязательна — регистрация (ТЗ 3.1)
  собирает только номер, и записи, заведённые ею, о родстве не знают. Пустая строка снимает;
- **имя и фамилия необязательны** по той же причине;
- **телефон нельзя очистить** (400) и нельзя сменить на занятый другим родителем (409):
  слияние двух записей молча перенесло бы детей одной на другую;
- **отвязка последнего ребёнка удаляет запись целиком** (`parentDeleted: true`): без детей
  она недостижима — ни найти, ни исправить. У родителя с другими детьми запись остаётся.

**Колонки `Student.parentPhone` больше нет.** Телефон родителя из формы регистрации
(ТЗ 3.1) теперь заводит запись `Parent`, а миграция `20260729000000_phase4_parents`
перенесла существующие номера (одинаковые сведены в одну запись). В форме карточки
студента поля родительского телефона нет и не было — ТЗ 5.3 его не перечисляет; попытка
передать `parentPhone` в `POST/PUT /students` вернёт 400. Сами контакты видны в карточке
списком `parents`.

#### Кабинет студента (ТЗ 5.3: «только просмотр»)

```http
GET /api/v1/me              → свой профиль
GET /api/v1/me/groups       → свои группы (курс, менторы, статус членства)
GET /api/v1/me/schedule     → своё расписание (занятия действующих групп)
GET /api/v1/me/performance  → свои баллы и своё место в рейтинге
```

Первый контур проекта, доступный **студенту**: всё остальное закрыто
`@RequireAccountType(EMPLOYEE)`.

- **адрес `/me`, а не `/students/{id}` с проверкой «это я»**: студенту нужны не те же
  выборки с фильтром, а другие — «мои группы» это членства с курсом и менторами, а не
  строка списка админ-стороны. Заодно ни один уже написанный эндпоинт не пришлось ветвить
  по типу вызывающего, а забытая ветка открыла бы студенту чужие данные;
- **идентификатор студента в запросах не участвует вообще** — профиль выводится из токена,
  поэтому «посмотреть чужое» здесь нечем даже при ошибке в коде;
- **прав каталога у кабинета нет и быть не может**: права даются позициями, а позиции есть
  только у сотрудников (ТЗ 3.2). Доступ ограничивает тип аккаунта; сотрудник получает 403 —
  витрина сотрудника (ТЗ 5.4) появится вместе с его профилем в Фазе 6;
- **профиль без внутренних данных центра**: заметок администратора (`notes`), заметок
  сотрудников (Feedback) и данных аккаунта в ответе нет. Контакты родителей есть — студент
  и так их знает, и они часть его же карточки;
- **свои группы включают закрытые членства** — это учебная история (`status=ACTIVE`
  оставит только текущие). По умолчанию свежие сверху;
- **расписание — только действующих членств**: покинутая группа остаётся в «моих группах»
  историей, но её занятия к расписанию человека больше не относятся. Слот повторяется
  еженедельно («понедельник, 10:00–12:00»), разворот в календарь Day/Week/Month — ТЗ 5.10,
  Фаза 10. Фильтр `groupId` действует в пределах своих действующих групп: чужая
  и несуществующая отвечают одинаковым 422, иначе кабинет работал бы способом перебрать
  группы центра;
- **заблокированному кабинет закрыт (403)** — единственное место проекта, где блокировка
  действует сразу, не дожидаясь, пока истечёт выданный access-токен: профиль здесь и так
  читается на каждый запрос, поэтому проверка бесплатна;
- **свои баллы и свой рейтинг — один маршрут**: место выводится из общего балла (ТЗ 5.8,
  5.13), и разделять их значило бы считать одно и то же дважды. Ответ **тот же**, что
  у `GET /students/{id}/performance`, вплоть до типа: копия DTO развела бы одни и те же
  числа по двум формам, и расхождение между «моим баллом» и баллом в карточке всплыло бы
  не отказом, а спором студента с ментором (на совпадение ответов есть e2e-тест).

Все пять разделов ТЗ 5.3 закрыты: профиль, группы, расписание, свои баллы и рейтинг.

### Журнал / Progressbook (ТЗ 5.8)

Журнал вложен в группу: неделя не существует отдельно от неё. Неделя — это учебные дни
плюс таблица «студент × день», в клетке которой посещаемость (`Att`) и балл за домашнее
задание (`Score`, до 5).

- **дни недели задаёт оператор**, а не расписание группы: слоты (`ScheduleSlot`) описывают
  план и повторяются еженедельно, журнал же фиксирует **факт** — занятие могло не состояться
  или пройти не по плану;
- **дни укладываются в семь суток от начала недели** (400 иначе). Без этого «неделя»
  перестала бы что-либо означать: в неё поместился бы месяц занятий, а `Sum` считался бы
  по произвольному отрезку — при том, что общий балл студента это среднее по неделям;
- **один календарный день не входит в две недели группы** — 409 с номером занявшей недели:
  иначе приход за него посчитался бы дважды;
- **номер недели назначает система** (`max + 1`): два способа задать один и тот же порядок
  разошлись бы на первой же вставке недели в середину;
- **итог недели** `Sum = Σ(приходы) + Σ(ДЗ) + Exam + Bonus`, и **на экзамене приход
  не считается**: за экзаменационный день балл приходит слагаемым `Exam`, а начислять
  за него ещё и приход значило бы посчитать день дважды. Домашнее задание засчитывается
  в любой день — ТЗ исключает только приход;
- **опоздание (`LATE`) считается приходом**: человек на занятии был. Отдельная отметка
  нужна графику посещаемости из ТЗ 5.2, а не штрафу, которого ТЗ не просит;
- **`null` в клетке — «не отмечен», а не «отсутствовал»**: разные состояния, и первое
  не должно попадать в отчёт по пропускам;
- в `PUT` **`days` заменяет** набор дней целиком (убранный день уносит свои отметки),
  а `entries` и `results` — точечные правки: в клетке `null` снимает отметку, отсутствие
  поля её не трогает;
- **итоги пересчитываются всем студентам недели**, а не только тем, чьи клетки тронуты:
  убранный день меняет `Sum` каждому, кто в него приходил. `WeekResult.sum` хранится
  ради среднего балла и рейтинга (ТЗ 5.13), но пересчитывается той же транзакцией,
  что и правка, — второго источника истины не возникает;
- **«отметить всех присутствующими»** заполняет только **неотмеченные** клетки
  действующего состава: уже проставленные пропуски кнопка не переписывает, восстановить
  их было бы неоткуда. Без `date` — все дни недели, с датой — один;
- **отмечать можно тех, кто состоит или состоял в группе** (422 иначе), а отметки
  ушедшего из состава в неделе остаются: журнал не переписывается задним числом;
- **финализация («Отправить результат»)** одной транзакцией блокирует неделю, начисляет
  коины и собирает отчёт Директору. Повторная — 409, неделя без учебных дней — 422.
  После неё неделя не правится и не удаляется (422): по её итогам уже выданы коины;
- **удаление недели** есть сверх перечня ТЗ: заведённая по ошибке неделя навсегда
  искажала бы средний балл студента.

Доставка отчёта Директору (Telegram/почта) появится с уведомлениями Фазы 11 — сейчас
он возвращается в ответе на `submit` и пишется в лог приложения.

### Коины (ТЗ 5.9)

- **списание запрещено**: сумма только положительная (400 на ноль и отрицательное),
  история не правится и не удаляется. Отобрать выданное нечем по устройству модуля,
  а не по забытой проверке;
- **баланс равен сумме начислений** и отдаётся в `meta.balance` рядом с историей —
  он один на все страницы, и отдельный запрос ради одного числа был бы лишним;
- **автоначисление по итогам недели**: `≥100 → 5 · 90–99 → 4 · 85–89 → 2 · <85 → 0`.
  Нулевая строка в историю не пишется — она ничего не сообщает, а засоряла бы её
  каждую неделю. Одно автоначисление на студента за неделю держит уникальный индекс;
- **ручное начисление требует причины** (≥3 символа), автор берётся из токена;
- начисляет коины журнал — той же транзакцией, что и финализирует неделю, — но по правилу
  `coinsForWeekSum` из модуля коинов: две копии порогов разошлись бы на первой же правке.

### Успеваемость: общий балл, категории, рейтинг (ТЗ 5.3, 5.5, 5.8, 5.13)

`GET /students/{id}/performance` — витрина поверх журнала: своих таблиц у неё нет,
всё выводится из `WeekResult` и `JournalEntry`. Модели `Performance` из карты ТЗ 4
**не заведено**: балл считается агрегатом на лету, поэтому правка журнала видна
в рейтинге сразу и второго источника истины о том же числе не возникает.

- **общий балл = среднее `Sum` по неделям** (ТЗ 5.8), и в него входят **только
  финализированные** недели. Открытая неделя заводится с нулевыми итогами на весь
  состав, поэтому при учёте всех недель средний балл обрушивался бы каждый понедельник
  и восстанавливался к пятнице — вместе с категорией активности и короной. Коины
  по ТЗ 5.9 начисляются тоже при финализации: балл и коины опираются на одни недели;
- **балла может не быть**: у студента без единой закрытой недели `averageScore: null`,
  а не ноль — ноль записал бы его в Black list за то, что его группа просто ещё
  не дошла до первой финализации;
- **категории активности** (ТЗ 5.5) выводятся из балла: `ChatGPT ≥95 · Handsome 80–94 ·
  Advanced 65–79 · Kettle 45–64 · Black list <45`. **«Passing students»** — те, кто
  не в Black list; порог не задан вторым числом, а выведен из той же таблицы;
- **рейтинг и корона** (ТЗ 5.3, 5.13) охватывают только тех, кто **учится сейчас**
  (есть действующее членство): иначе корона навсегда осталась бы у выпускника прошлого
  года. У выпускника балл виден, а места в рейтинге нет (`ranked: false`);
- **место = «сколько выше, плюс один»**: при равенстве баллов оба занимают одно место
  и корона достаётся обоим — придуманное правило разрыва ничьей поставило бы одного
  из двух одинаково успевающих ниже без основания. Сравнения идут по **неокруглённому**
  значению, наружу балл уходит округлённым до двух знаков;
- **посещаемость** считается по **всем** отмеченным дням, а не только по закрытым
  неделям: пропуск — это факт, а не начисление. Опоздание относится к приходам —
  тем же правилом, что и балл за приход (ТЗ 5.8);
- **разрез по группам** идёт от членств, а не от итогов: группа, в которой ещё ни одной
  недели не закрыли, остаётся в списке с баллом `null`, иначе «мои группы» и «моя
  успеваемость» показывали бы разный состав.

В строке списка студентов рядом с баллом стоят `activityCategory` и `isTopStudent`
(корона), в строке списка групп — `activity` (счётчики категорий) и `passingCount`.
**Счётчики группы считаются по её собственным неделям** и по действующему составу:
они стоят на карточке группы, и от учёбы человека на соседнем курсе сдвигаться
не должны. Не оценённые идут в `unscored`, а не в Black list.

### Лидеры и победители месяца (ТЗ 5.13)

`GET /api/v1/leaders` — рейтинг центра, `GET/POST /api/v1/leaders/winners`
и `DELETE /api/v1/leaders/winners/{month}` — снимок месяца. Просмотр закрыт
`Permission.Leaders.Views`, закрытие месяца — `Permission.Leaders.ManageWinners`.

**Рейтинг** считается на каждый запрос теми же правилами, что и витрина успеваемости
(общий балл, только финализированные недели, только учащиеся сейчас):

- **топ-3 отдаётся в `meta.top`**, а не только первыми строками первой страницы:
  он один на все страницы, и на второй странице экран не должен терять пьедестал —
  тот же приём, что с балансом коинов в `meta.balance`;
- **места считаются по всему рейтингу**, а страница нарезается уже из него:
  на вопрос «сколько выше меня» нельзя ответить, прочитав двадцать строк;
- **фильтры `groupId`/`courseId` считают балл по неделям среза**, а не общий. Иначе
  рейтинг внутри группы сравнивал бы её студентов числом, в которое входит учёба
  на соседнем курсе, и разошёлся бы со счётчиками карточки группы;
- **`order=asc` показывает отстающих**, и места при этом остаются настоящими:
  переворачивается порядок показа, а не нумерация.

**Победители месяца** — единственное место успеваемости, где посчитанное **хранится**
(`MonthlyWinner`). Причина обратна той, по которой не заведён `Performance`: снимок
обязан пережить последующие правки журнала, иначе правка старой недели задним числом
молча переписала бы прошлогодних победителей.

- **месяц закрывается осознанным действием** (`POST /leaders/winners`), как неделя
  журнала — «Отправить результат». Фоновой задачи нет: до Фазы 11 в проекте не работает
  ни одна, и вешать на них первую живую логику рано;
- **победитель месяца — лучший за этот месяц**, а не лидер общего рейтинга на его конец:
  считается среднее `Sum` по финализированным неделям месяца, и неделя относится
  к месяцу **своей даты начала**. Иначе победитель не менялся бы, пока лидер держит
  первое место;
- **фильтра «учится сейчас» здесь нет**, в отличие от живого рейтинга: снимок отвечает,
  кто учился лучше всех **тогда**, и отбор по сегодняшнему статусу вычеркнул бы из июня
  того, кто закончил курс в июле;
- **`places` ограничивает число мест, а не строк** (по умолчанию 3, ТЗ 5.13): при ничьей
  на последнем месте в снимок попадают все, кто его занял;
- **повторное закрытие — 409**: снимок не пересчитывается. Незавершившийся месяц — 422
  (заморозил бы неполные данные), месяц без единой финализированной недели — тоже 422;
- **`GET /leaders/winners` без `month`** отдаёт последний **закрытый** месяц («Winners
  of the last month»). Незакрытый месяц — это `closed: false` и пустой список, а не 404;
- **`DELETE /leaders/winners/{month}`** — сверх перечня маршрутов ТЗ: без него ошибочно
  закрытый месяц остался бы навсегда, ведь повторное закрытие отклоняется. Право то же,
  что у закрытия;
- **попавший в снимок студент не удаляется** (409): `DELETE /students/{id}` называет
  победы в рейтинге месяца среди причин отказа рядом с журналом и коинами.

### Сотрудники (ТЗ 5.14)

`GET/POST /api/v1/employees`, `GET/PUT/DELETE /api/v1/employees/{id}` — список,
карточка «Employer» и форма (ФИО, ДР, телефон, email, адрес, Position, Experience,
Branch, Telegram, Description, фото).

- **профиль заводится без аккаунта**: ТЗ 5.14 называет логин опциональным. Он появляется
  переводом студента (ТЗ 3.1) или сид-скриптом `npm run seed:admin`; фильтр
  `?hasAccount=false` показывает тех, у кого его нет;
- **телефон уникален среди сотрудников** (409 с именем владельца) и нормализуется
  в E.164 — конфликт ловится и на номере в другом формате;
- **фильтры**: `status`, `branchId` (ТЗ 3.3), `positionId` и `hasAccount`; поиск `search` —
  по имени, фамилии, отчеству, телефону и email. **Фильтр по позиции и есть список
  менторов** (ТЗ 5.4): ментор — это сотрудник с соответствующей позицией, а не отдельная
  сущность, и второй маршрут отвечал бы на тот же вопрос иначе;
- **несуществующий филиал в теле — 422**, пустая строка в `branchId` снимает привязку;
  пустая строка в необязательном поле `PUT` очищает его, не переданное — оставляет прежним.

**Позиции в форме требуют второго права.** ТЗ 5.14 перечисляет «Position (мультивыбор)»
полем формы, но позиция — это роль доступа (ТЗ 3.2), и назначение ролей ТЗ 5.15 закрывает
своим правом. Поэтому `positionIds` дополнительно требуют
`Permission.Administration.ManageUserRoles` (403 без него): приняв их под
`Permission.Employees.Update`, мы сделали бы право на правку карточки правом раздать себе
`Director` вместе с бухгалтерией (ТЗ 5.16). Форма **без** мультивыбора — обычная правка
и второго права не спрашивает. Набор заменяется целиком (пустой массив снимает все
позиции), несуществующая — 422 с перечислением только недостающих.

**`INACTIVE` закрывает вход.** Перевод сотрудника в «выведен из штата» одной транзакцией
ставит `Account.status = BLOCKED` и гасит его сессии; возврат в `ACTIVE` вход открывает.
«Уволен» и «может войти со всеми правами своих позиций» — состояния, которые не должны
существовать одновременно; это то же решение, что у блокировки студента (ТЗ 5.3).
Сохранение карточки без смены статуса сессии не гасит.

**Последний действующий `Director` неприкосновенен** (422): его нельзя ни разжаловать,
ни вывести из штата, ни удалить. Все три пути ведут к одному — бухгалтерия доступна только
этой позиции (ТЗ 5.16), а вернуть её мог бы лишь тот, у кого есть право назначать роли.
Уволенный руководитель за действующего не считается: вход ему закрыт, и систему он
не разблокирует.

**Удаляется только «чистый» профиль** (409): сотрудник, который ведёт группы, стоит
в расписании, закрывал недели журнала, писал заметки о студентах или начислял коины,
не удаляется — вместе с ним эти записи остались бы без автора, а менторство ушло бы
каскадом. Для «человек больше не работает» есть `INACTIVE`. Аккаунт удаляется вместе
с профилем: логина без профиля ТЗ 3.1 не допускает.

### Уровни ментора (ТЗ 5.14, 5.4)

Справочник ступеней центра и **помесячная** история сотрудника. Помесячность — не форма
хранения, а требование расчёта: зарплата считается по ставке уровня **того месяца**,
за который начисляется (ТЗ 5.16), поэтому повышение в октябре не должно менять сумму
за сентябрь.

`GET/POST /api/v1/mentor-levels`, `GET/PUT/DELETE /api/v1/mentor-levels/{id}` — справочник:

- ступень = название + описание + **часовая ставка** в сомони (`DECIMAL(12,2)`, наружу —
  числом) + статус. Фильтр `status`, поиск `search` по названию и описанию, сортировка
  `name|hourlyRate|createdAt`; по умолчанию — по возрастанию ставки, лестницу читают снизу вверх;
- **название уникально без учёта регистра** (409): «Senior mentor» и «senior mentor»
  человек читает как одну ступень;
- **ставка живёт в справочнике, а не копируется в месяц**: её пересматривают для всей
  лестницы разом, и копия у каждой записи истории означала бы правку N строк вместо одной.
  Обратная сторона названа честно: правка ставки меняет расчёт **за все** проставленные
  месяцы. Чтобы этого избежать, заводят новую ступень, а старую переводят в `INACTIVE`;
- **ступень, проставленную хотя бы в одном месяце, удалить нельзя** (409 с числом месяцев):
  по ней считается зарплата. Для «ступень больше не используем» есть `INACTIVE` — новым
  месяцам она не проставится, а прошлые сохранят ставку.

`GET/PUT /api/v1/employees/{employeeId}/mentor-levels`,
`DELETE …/mentor-levels/{month}` — уровень сотрудника по месяцам:

- месяц — `YYYY-MM` (в БД лежит первым числом, `@db.Date`); ставка ступени отдаётся
  рядом с месяцем, чтобы экран не догружал справочник;
- **одна запись на сотрудника в месяц**: `PUT` идемпотентен и меняет ступень месяца,
  а не заводит вторую строку. Две записи о ставке одного месяца заставили бы расчёт
  зарплаты выбирать между ними;
- **месяц без записи означает, что уровня в нём не было** — ближайший предыдущий сюда
  не тянется. Пробел виден, а не заполнен догадкой, и ошибка обнаруживается до выплаты;
- фильтры `from`/`to` (месяцы, включительно) и `levelId`; по умолчанию свежие сверху.
  Период заведён сверх перечня ТЗ: зарплатная ведомость считается за отрезок (ТЗ 5.16);
- несуществующая ступень в теле — 422; **выведенная из справочника (`INACTIVE`) — тоже 422**,
  но уже проставленная остаётся: запрет касается только новых месяцев (то же, что
  с `INACTIVE` сотрудником в менторах группы);
- `DELETE …/{month}` нет в перечне ТЗ, но без него ошибочно проставленный месяц нельзя
  было бы убрать. Право то же, что у простановки;
- **позиция «Mentor» не требуется** — по той же причине, по которой она не требуется
  для назначения ментором группы: правило держалось бы на переименуемом названии позиции.

Права: справочник — `Permission.MentorLevels.Views|Create|Update|Delete`; история —
`Permission.Mentors.Views` на просмотр и `Permission.Mentors.ManageLevels` на изменение.
Видеть, на какой ступени человек, нужно всем, кто работает с менторами, а двигать
ступени — не всем.

### Заявки на аванс (ТЗ 5.14, 5.16)

`GET/POST /api/v1/employees/{employeeId}/avans`, `DELETE …/avans/{avansId}` — подача
и просмотр заявок. **Рассмотрение здесь не живёт:** `Approve/Deny` относится
к бухгалтерии (`/accounting/avans/{id}/approve|deny`, ТЗ 5.16) и появится в Фазе 9 —
одобрение превращает заявку в `Prepaid` расчёта зарплаты.

- заявка = **сумма** в сомони (`DECIMAL(12,2)`, наружу числом) + обязательная **причина**
  + **месяц зарплаты** (`YYYY-MM`), из которой удержится аванс. Месяц, а не дата: `Prepaid`
  по ТЗ 5.16 относится к месяцу, и заявка за сентябрь, одобренная 2 октября, иначе легла
  бы не в тот расчёт;
- **заявку заводит сотрудник с правом `Permission.Avans.Create`** — в том числе от имени
  ментора. Автор берётся из токена, подать её от чужого имени нельзя. Сам ментор подаёт
  заявку **о себе** через кабинет (`POST /api/v1/mentor/avans`) — там права не требуется,
  см. раздел «Кабинет ментора»;
- **одна нерассмотренная заявка на сотрудника** (409 с суммой и месяцем существующей).
  Иначе оператор, не увидевший первую, заводил бы дубль, бухгалтерия одобрила бы обе,
  а отменить выплату было бы нечем. Рассмотренные заявки подаче следующей не мешают;
- **выведенный из штата (`INACTIVE`) новых заявок не подаёт** — 422; уже поданные
  остаются и отзываются как обычно. Та же асимметрия, что у `INACTIVE` сотрудника
  в менторах группы и выведенной ступени уровня;
- **отзывается только нерассмотренная заявка** (`PENDING`); рассмотренная — 422: она уже
  вошла в расчёт месяца, и стирать её значило бы переписывать зарплатную историю.
  Маршрута отзыва нет в перечне ТЗ, но без него ошибочная заявка закрывала бы сотруднику
  подачу следующей до самой Фазы 9. Право то же, что у подачи;
- заявка **не правится**: сумму и причину меняют отзывом и новой подачей — правка после
  рассмотрения означала бы деньги, выданные не по тому, что одобряли;
- список: фильтр `status`, период по месяцу зарплаты (`from`/`to`, включительно),
  сортировка `createdAt|month|amount`, по умолчанию свежие сверху. Заявка ищется вместе
  с сотрудником из адреса: через `/employees/A/avans/{id}` заявка сотрудника B
  не найдётся (404).

Права: `Permission.Avans.Views` на просмотр, `.Create` на подачу и отзыв.
`Permission.Avans.Approve` в каталоге есть, но пока никем не требуется — он достанется
маршрутам одобрения в Фазе 9.

### Кабинет ментора (ТЗ 5.4: Profile, Groups, Material, Timetable, Courses)

`GET /api/v1/mentor/profile|groups|timetable|courses|materials`,
`GET/POST /api/v1/mentor/avans`, `DELETE …/avans/{avansId}` — второй контур «своё»
в проекте, после кабинета студента. Адрес свой, а не `/me`: тот принадлежит студенту,
и ветвить его по типу вызывающего значило бы завести ветку, забыв которую, открываешь
чужие данные.

Как это устроено:

- **всё адресуется от токена.** Идентификатор сотрудника в запросах не участвует:
  профиль выводится из аккаунта вызывающего, поэтому «посмотреть чужое» здесь нечем;
- **каждая выборка сужена менторством** (`mentors: { some: { employeeId } }`), а не
  проверкой после выборки: чужие группы, курсы и материалы не попадают сюда
  по построению;
- **прав каталога нет.** Кабинет отдаёт только то, что и так принадлежит вызывающему, —
  требовать за это право значило бы завести право «видеть себя» и выдавать его каждому
  сотруднику поимённо. Обратная сторона: того, на что права нужны, кабинет и не
  показывает — **состава групп** (это `GET /groups/{id}/students` с `Permission.Groups.Views`),
  **стоимости курса** (`fee` — бухгалтерия, ТЗ 5.16) и чужих заявок;
- **выведенному из штата (`INACTIVE`) кабинет закрыт** — 403 на всех разделах, включая
  подачу аванса: `INACTIVE` означает и закрытый вход. Профиль читается на каждый запрос,
  поэтому запрет действует сразу, не дожидаясь истечения выданного access-токена;
- **позиция «Mentor» не требуется** — четвёртый раз то же решение: правило держалось бы
  на переименуемом названии позиции. Сотрудник без единой группы видит пустые разделы,
  а не отказ;
- аккаунт типа `EMPLOYEE` без профиля — 404, студент — 403.

Разделы:

- **Profile** — карточка вместе с **уровнем и часовой ставкой текущего месяца** (ТЗ 5.4).
  Месяц назван в ответе явным полем: значение зависит от того, когда задан вопрос.
  `level: null` — на этот месяц уровень не проставлен, и предыдущий сюда не тянется;
- **Groups** — группы под менторством с курсом, филиалом, своей ролью (Teaching/Support)
  и «набрано/вместимость»; фильтры `role` и `status`, поиск по названию группы и курса;
- **Timetable** — занятия своих групп. Отбор идёт **от менторства**, а не от ведущего
  на слоте: ведущий необязателен, и выборка по нему отдала бы пустое расписание почти
  каждому ментору. Кто ведёт лично, показывает поле `mine`; `onlyMine=true` оставит
  только свои занятия, `onlyMine=false` — занятия коллег и слоты без ведущего;
- **Courses** — курсы своих групп вместе с этими группами (одним запросом на страницу,
  а не на строку);
- **Material** — уроки, открытые своим группам через «Show to group» (ТЗ 5.6), вместе
  со ссылками на материалы. Это **не** вся программа курса: она читается
  `GET /courses/{id}/lessons` и требует `Permission.Syllabus.Views`;
- **Avans** — свои заявки: список, подача о себе и отзыв нерассмотренной. Правила те же,
  что на админ-стороне (одна `PENDING`, месяц обязателен, рассмотренная не отзывается) —
  кабинет **переиспользует** тот же сервис, а не повторяет их. Права `Avans.Create`
  здесь нет намеренно: оно означает «завести заявку любому сотруднику», и выдав его
  каждому ментору, мы открыли бы подачу за коллег.

**Раздела «SMS mailings» из меню ТЗ 5.4 здесь нет:** рассылки — Фаза 11, и раньше неё
маршрут отдавал бы пустоту, ничего не обещая.

### Силлабус курса (ТЗ 5.6)

Программа курса вложена в сам курс — она не существует отдельно от него, и адрес урока
сам подтверждает, какому курсу он принадлежит.

- **номер дня («Day N») не уникален**: в один учебный день может стоять и лекция,
  и практика. Номер задаёт порядок в списке, а не тождество урока;
- **урок ищется внутри своего курса**: через `/courses/A/lessons/{id}` урок курса B
  не найдётся (404). То же для материала внутри урока — иначе адрес не защищал бы ничего;
- **«Show to group»** (`visibleToGroupIds`) принимает только группы **этого же курса** —
  422 с перечислением лишних. В `PUT` список **заменяет** мультивыбор целиком, пустой
  массив снимает всех, а не переданное поле мультивыбор не трогает;
- у урока два независимых перечисления из ТЗ: `type` занятия (`LECTURE`/`PRACTICE`/`EXAM`)
  и `status` (`ACTIVE`/`INACTIVE` — скрыть урок, не теряя материалы);
- у материала тоже два: `kind` — **зачем** файл (`LECTURE`/`PRACTICE`/`HOMEWORK`),
  `fileType` — **что** это за файл (`PDF`, `VIDEO`, `LINK`…, для иконки и способа открытия);
- **материалы — ссылки на внешнее хранилище**, а не загружаемые файлы: приём загрузок —
  отдельный кусок инфраструктуры, модель к нему готова без миграции;
- **удаление урока уносит его материалы и мультивыбор** (каскад). Отказа здесь нет:
  файл вне урока адресовать нечем, а видимость — настройка экрана, а не данные.

### Управление правами

| Эндпоинт | Назначение | Требуемое право |
|---|---|---|
| `GET /api/v1/positions` | Справочник позиций (пагинация, поиск) | `Permission.Positions.Views` |
| `GET /api/v1/positions/{id}` | Карточка позиции с кодами её прав | `Permission.Positions.Views` |
| `POST /api/v1/positions` | Создание позиции с галочками прав | `Permission.Positions.Create` |
| `PUT /api/v1/positions/{id}` | Правка позиции; `permissions` заменяет набор целиком | `Permission.Positions.Update` |
| `DELETE /api/v1/positions/{id}` | Удаление позиции | `Permission.Positions.Delete` |
| `GET /api/v1/admin/users` | Все аккаунты: Type / Roles / Phone (ТЗ 5.15) | `Permission.Administration.ViewUsers` |
| `POST /api/v1/admin/users/{id}/roles` | Назначить позиции аккаунту сотрудника | `Permission.Administration.ManageUserRoles` |
| `DELETE /api/v1/admin/users/{id}/roles` | Снять позиции (список — в теле запроса) | `Permission.Administration.ManageUserRoles` |
| `GET /api/v1/admin/permissions` | Каталог прав по разделам с переключателями | `Permission.Administration.ViewPermissions` |
| `PUT /api/v1/admin/permissions` | Переключить права каталога | `Permission.Administration.ManagePermissions` |

Правила, которые стоит знать заранее:

- **раздел Accounting доступен только позиции `Director`** (ТЗ 3.2, 5.16): выдать
  `Permission.Accounting.*` любой другой позиции нельзя — 422. Список закрытых разделов —
  `DIRECTOR_ONLY_SECTIONS` в `src/rbac/rbac.constants.ts`;
- **системная позиция `Director` неизменяема**: правка, переименование и удаление — 422;
- **позицию, которую занимают сотрудники, удалить нельзя** (409): каскад молча забрал бы
  у них часть прав, и восстановить, какие именно, было бы нечем;
- название позиции уникально **без учёта регистра** — иначе `director` рядом с `Director`
  читался бы как та же позиция, а правило доступа сработало бы только для одной из них;
- **последнего `Director` разжаловать нельзя** (422): назначение ролей само требует права,
  и вернуть доступ было бы некому;
- роли назначаются только аккаунтам **сотрудников** (студенту — 422) и начинают действовать
  **сразу**, без повторного входа: права читаются из БД на каждый запрос;
- **служебные права** (`Permission.Administration.ViewPermissions` и `...ManagePermissions`)
  выключить нельзя — иначе управление каталогом не вернуть через API;
- `GET /admin/permissions` **не постраничный**: это экран настроек, где раздел нужен целиком
  (`?section=Students` оставляет один раздел).

## Переменные окружения

Все переменные валидируются при старте (`src/config/env.validation.ts`); при некорректном
значении приложение не поднимется. Полный список с описанием — в `.env.example`.
Секреты хранятся только в `.env` (в git не попадает).

`JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` и `PASSWORD_RESET_SECRET` обязательны, минимум
32 символа и **разные**: access-токен, утёкший в логи прокси, не должен приниматься как refresh,
а секрет кодов сброса не должен зависеть от компрометации подписи токенов. Сгенерировать:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

    правами — включая «выдали роль → доступ появился» и «выключили право в каталоге →
    доступ пропал», связки учебного контура («группа держит курс и филиал»), правила
    силлабуса («урок чужого курса не найдётся», «Show to group» только своим группам)
    и менторов группы («один сотрудник — одно назначение», «ментор соседней группы
    по этому адресу не найдётся»), расписания («аудитория занята другой группой»,
    «аудиторию с занятиями не удалить») и состава группы («одна группа на курс»,
    «перевод закрывает прежнее членство», «группу с составом не удалить», «файл выгрузки
    принимается импортом обратно», «плохая строка отменяет весь импорт») и карточки
    студента («телефон занят», «профиль с учебной историей не удалить», «уход из последней
    группы переводит профиль в No Active»), доступа студента («пригласили → студент прочитал
    письмо → задал пароль по коду → вошёл», «заблокированный не обновляет токены»)
    и обратной связи («заметка подписана сотрудником из токена», «заметка о соседнем
    студенте по этому адресу не найдётся») и родителей («второму ребёнку привязывается
    та же запись, а не копия», «правка контактов видна у второго ребёнка, а родство — нет»,
    «отвязка последнего ребёнка удаляет запись») и кабинета студента («каждый получает
    свой профиль, а не чужой», «расписание покинутой группы в кабинет не попадает»,
    «сотруднику кабинет закрыт», «заблокированному закрыт целиком», «кабинет и карточка
    показывают один и тот же балл») и сотрудников («позиции без права на роли — 403»,
    «перевод в INACTIVE блокирует аккаунт и гасит сессии», «последнего Director нельзя
    ни разжаловать, ни уволить, ни удалить», «уволенный руководитель за действующего
    не считается») и уровней ментора («повышение в октябре не трогает сентябрь»,
    «повторная простановка меняет ступень месяца, а не заводит вторую строку»,
    «новая ставка справочника видна во всех проставленных месяцах», «ступень,
    по которой считали зарплату, не удалить») и авансов («вторая нерассмотренная
    заявка — 409», «отозвал первую — вторую подать можно», «рассмотренная заявка
    подаче не мешает», «рассмотренную не отозвать», «заявка соседнего сотрудника
    по этому адресу не найдётся») и кабинета ментора («ментор подаёт заявку сам,
    без права каталога, и она подписана им же», «заявка из кабинета видна
    на админ-стороне тем же телом», «группы и материалы соседнего ментора
    не попадают», «урок открыт двум группам — в ответе только своя», «занятие
    без назначенного ведущего остаётся в расписании», «выведенному из штата
    закрыт целиком») и журнала
    («на экзамене приход не считается», «убранный день уносит свои баллы»,
    «кнопка не переписывает проставленный пропуск», «финализированная неделя
    не правится», «повторная финализация не начисляет коины дважды») и коинов
    («баланс складывается из начислений», «списание — 400», «баланс в `meta`»)
    и успеваемости («открытая неделя в общий балл не входит», «выпускник в рейтинге
    не участвует, но балл у него остаётся», «при равенстве баллов корона у обоих»,
    «покинувший группу в её счётчики не входит», «карточка и витрина показывают
    один и тот же балл») и лидеров («правка журнала задним числом победителей
    месяца не меняет», «в снимок попадает и тот, кто уже не учится», «недели
    соседнего месяца в снимок не идут», «повторное закрытие — 409», «снял снимок →
    месяц можно закрыть заново», «балл среза считается по неделям этой группы»,
    «на второй странице пьедестал остаётся в `meta`») проверяются на любой машине);
  - `health.e2e-spec.ts` требует поднятых PostgreSQL и Redis (запускается в CI
    и через `docker compose`).

  group-journal/ журнал группы: недели, дни, Att + Score, Bonus/Exam/Sum,
