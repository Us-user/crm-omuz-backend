# Сессия 0041 — Деплой на Render: Blueprint, REDIS_URL и первый руководитель

- **Дата:** 2026-08-04
- **Фаза roadmap:** Фаза 14 — Финализация и hardening (пункт «инструкции деплоя»)
- **Статус сессии:** завершена

## Цель сессии

Не следующий пункт roadmap, а **запрос пользователя**: залить проект на Render
хотя бы один раз, чтобы фронтенд мог работать против настоящего API.

Пункт «README, инструкции деплоя» в Фазе 14 существовал, но задача пришла
раньше очереди, и это правильно: живой API нужен фронту сейчас, а не после
локализации и индексов.

## Три блокера, найденных до кода

Разбор кода с точки зрения деплоя выявил три вещи, каждая из которых
в одиночку сделала бы деплой бесполезным:

1. **`REDIS_URL` не поддерживался.** Render (и любой облачный провайдер)
   выдаёт одну строку подключения, а конфигурация требовала
   `REDIS_HOST`/`PORT`/`PASSWORD`/`DB` по отдельности — причём в двух местах
   сразу (`RedisService` и BullMQ).
2. **Первого `Director` нечем было завести.** `npm run seed:admin` идёт через
   `ts-node`, а на бесплатном плане Render **нет shell**. Без руководителя
   в CRM не войти никому: регистрация создаёт только студентов (ТЗ 5.14),
   а раздача ролей требует прав, которых на пустой базе нет ни у кого.
   То есть деплой был бы формально успешным и полностью бесполезным.
3. **Миграции никто не применял бы** — `prisma migrate deploy` не был вписан
   ни в один сценарий запуска, кроме `docker-compose`.

## Четыре решения, вынесенные пользователю

1. **Redis заводим сразу** (Render Key Value) — после объяснения, что он делает
   в проекте. Без него воркер рассылок бесконечно переподключался бы и засорял
   лог, `/health` был бы вечно `degraded`, а рассылки, расписание и лимиты
   мертвы.
2. **Первый руководитель — автосидом при старте** по `SEED_ADMIN_*`
   (единственный вариант без shell).
3. **CORS — локальный фронт**: `http://localhost:5173` и `http://localhost:3000`.
4. **Нативный Node-рантайм Render**, а не наш `Dockerfile`.

Факты о площадке проверены по документации Render, а не по памяти
(бесплатная база истекает через 30 дней, веб-сервис засыпает после 15 минут
простоя, Key Value без персистентности, shell на free недоступен).

## Что сделано

### `REDIS_URL` (`src/config/redis-url.ts`)

Чистая функция `parseRedisUrl` разбирает `redis://`/`rediss://` в поля
`host`/`port`/`username`/`password`/`db`/`tls`. `AppConfigService.redis`
отдаёт готовые параметры, `RedisService` и `QueueModule` их разворачивают —
включая `tls: {}` для `rediss://` и ACL-пользователя.

### Заведение первого руководителя при старте (`src/seed`)

- `AdminSeedBootstrap` (`OnApplicationBootstrap`) — читает `SEED_ADMIN_*`
  и вызывает **существующий** `AdminSeedService`;
- `SeedBootstrapModule` — отдельно от `SeedModule` (тот собирается для CLI
  своим контекстом);
- шесть переменных в схеме окружения, `AppConfigService.seedAdmin`
  и `seedAdminPartiallyConfigured`.

### `render.yaml`

Blueprint на три сервиса: `omuz-postgres` (free, PG 16), `omuz-keyvalue`
(free, `ipAllowList: []` — только внутренние подключения) и `omuz-api`
(нативный node, free, health-check `/health`). Строки подключения — через
`fromDatabase`/`fromService`, три секрета — `generateValue: true`, данные
руководителя — `sync: false` (Render спрашивает при создании).

Сборка: `npm ci && npx prisma generate && npm run build`.
Старт: `npx prisma migrate deploy && node dist/main.js`.

### README

Раздел «Деплой на Render»: пять шагов, что происходит при деплое, почему
не Docker, особенности бесплатных планов, CORS и `TRUST_PROXY`.

## Принятые решения

- **`REDIS_URL` перекрывает четыре отдельные переменные, а не дополняет их.**
  Два частично заполненных источника истины об одном адресе разошлись бы при
  первой правке, и отладка «почему подключается не туда» стоила бы дороже
  любой гибкости.
- **Строка разбирается в конфигурации, а не у каждого потребителя.**
  `RedisService` и BullMQ получают одинаковые поля одним путём; разбери они
  URL по отдельности — однажды разошлись бы по TLS, и это проявилось бы только
  на проде.
- **Пустые логин и пароль в URL — это «не задано», а не пустая строка.**
  У Render во внутреннем адресе аутентификации нет вовсе, а ioredis, получив
  пустую строку, попытается ею аутентифицироваться. Есть тест.
- **Плохой `REDIS_URL` роняет старт**, а не деградирует молча: приложение
  не должно подключаться в никуда (ТЗ 3.8, правило 0001).
- **Автосид — это не «эндпоинт первичной настройки».** Довод 0007 остаётся
  в силе: публичный путь к правам `Director` пришлось бы охранять, и он остался
  бы в приложении навсегда. Здесь новых возможностей не появляется — данные
  задаёт тот, кто управляет окружением сервиса, то есть и так всесилен.
- **Сбой сида не роняет приложение.** API работает и без руководителя,
  а упавший старт на площадке без shell лечить труднее, чем прочитать причину
  в логе (приём `ScheduledTasksRegistrar`, 0037).
- **Пароль при старте не генерируется.** Скрипт печатает сгенерированный
  в stdout, но у сервиса такого читателя нет, а писать пароль в журнал нельзя
  (довод писем на уровне `debug`, 0003). Поэтому `SEED_ADMIN_PASSWORD`
  обязателен, и об этом говорится ошибкой, а не молчанием. Есть тест на то,
  что пароль не попадает в лог **ни при каком исходе**.
- **Наполовину заполненный набор `SEED_ADMIN_*` — предупреждение, а не тишина.**
  Забытая переменная иначе оставила бы площадку без способа войти, и понять
  это было бы не по чему. Полное отсутствие переменных при этом молчит: на своей
  машине и в CI сид не настроен, и ругаться на это в каждом запуске — шум.
- **`SEED_ADMIN_PASSWORD` проверяется схемой окружения** (≥8): опечатка
  обнаруживается при старте, а не молчаливым «руководитель не завёлся»
  в середине лога.
- **`AdminSeedService` один на оба пути** (CLI и старт приложения). Второй
  экземпляр правил заведения руководителя разошёлся бы с первым молча — довод
  кабинета ментора про `AvansService` (0023).
- **Отдельный `SeedBootstrapModule`, а не расширение `SeedModule`.** Тот
  собирается для CLI своим контекстом и явно тянет `PrismaModule`,
  `PhoneModule`, `RbacModule` (вне `AppModule` глобальных модулей нет).
  Добавь в него `OnApplicationBootstrap` — скрипт сеял бы дважды: по окружению
  и по аргументам.
- **Зависимость от порядка модулей здесь мягкая.** `SeedBootstrapModule` стоит
  после `RbacModule`, потому что позицию `Director` восстанавливает
  синхронизация каталога. Но на чистой базе её заводит миграция, то есть
  до старта приложения; нарушение порядка стоило бы строки ошибки в логе,
  а не потери данных — в отличие от жёсткого «журнал раньше auth» (0038).
- **Нативный рантайм, а не `Dockerfile`** (решение пользователя). Образ
  собирается с `npm ci --omit=dev`, то есть без `prisma` CLI и `ts-node`:
  мигрировать и сеять в нём было бы нечем. Переделывать образ ради Render
  значило бы делать работу, которой не требует ни одна другая площадка.
- **Миграции в `startCommand`, а не в `buildCommand`.** Сборка на Render идёт
  до того, как сервис получает доступ к базе; кроме того, `migrate deploy`
  идемпотентен, и повторение при каждом старте безвредно.
- **`healthCheckPath: /health`** — эндпоинт отвечает 200 даже в состоянии
  `degraded` (0001), и это здесь важно: Render не должен перезапускать сервис
  из-за упавшего Redis, пока сам API работает.
- **Регион у всех трёх сервисов один** (`frankfurt`): иначе внутренние адреса
  недоступны и подключение пошло бы через интернет.

- e2e — **1259 тестов, 34 набора** без изменений: `health.e2e-spec.ts` поднимает
  полный `AppModule`, и он собирается с новым `SeedBootstrapModule`.
  Локально падает только он (2 теста) — нет пароля от локального PostgreSQL,
  известное состояние с сессии 0001.

**НЕ проверено (честно) — и это главный раздел лога:**

- **Сам деплой не выполнялся.** `render.yaml` не применялся, сервисы
  не создавались, приложение на Render не поднималось. Всё, что здесь есть, —
  подготовка; правильность Blueprint подтвердится только первым запуском.
- **`parseRedisUrl` ни разу не подключался к настоящему облачному Redis.**
  Разбор строки проверен юнит-тестами, но что ioredis с этими полями
  действительно соединяется с Render Key Value по TLS — принято на веру.
- **Автосид не выполнялся на живой базе.** Это ровно тот самый долг с сессии
  0007 («`seed:admin` ни разу не запускался»), и он **не закрыт, а расширен**:
  теперь непроверенных путей заведения руководителя два.
- **`npm ci` на чистой машине** (как это делает Render) локально
  не воспроизводился.
- **Lua-скрипт лимитера и задачи очереди** по-прежнему не проходили через
  настоящий Redis (0036–0040) — но именно этот деплой их и закроет.
- `docker compose` — Docker не установлен.

## Не доделано / известные проблемы

- **Бесплатная база Render истекает через 30 дней.** Это площадка для
  разработки фронта, а не хранилище данных, которые жалко.
- **Веб-сервис засыпает после 15 минут простоя** — первый запрос идёт до
  минуты. Фронтенду об этом надо сказать заранее, иначе он решит, что API
  сломан.
- **Key Value без персистентности**: при перезапуске очередь рассылок
  и счётчики лимитов пусты. Для счётчиков это норма, для очереди — потеря
  незавершённых доставок.
- **Живого провайдера писем нет** (решение 0036): сброс пароля и приглашения
  на проде **не работают**. Для первого руководителя это неважно — у него
  пароль из переменной, — но студент, забывший пароль, восстановить его
  не сможет.
- **Пароль руководителя лежит в переменных окружения Render** до тех пор, пока
  его оттуда не удалят. Сид его не меняет при перезапуске, так что удалять
  безопасно сразу после первого входа.
- **`openapi.yaml` как файл не выгружается** — документ отдаётся только
  по `/api/v1/docs/json`. Остаток пункта Фазы 14.
- **`StudentContractsService` обращается к Prisma напрямую** (долг Фазы 12).
- `npm audit` — те же high в дев-зависимостях.

## Следующий шаг

**Применить Blueprint и убедиться, что всё поднялось** — это единственное,
что имеет смысл делать дальше, и это же закроет сразу четыре записи
из «не проверено»: живой Redis (0036–0040), автосид (0007), `parseRedisUrl`
и сам деплой.

Порядок проверки после подъёма: `/health` → `up`/`up`/`up`, затем
`POST /api/v1/auth/login` данными руководителя, затем Swagger
на `/api/v1/docs`.

Если появятся ошибки — почти наверняка в одном из трёх мест: строка
подключения Key Value (TLS), права `npm ci` на dev-зависимости при сборке
или регион сервисов (внутренние адреса работают только внутри одного).

По roadmap следующим остаётся **локализация ru/en/tg** (ТЗ 3.3).
