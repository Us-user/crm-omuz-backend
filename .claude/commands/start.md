Ты продолжаешь разработку **бэкенда CRM «Omuz»** (обучающий центр, стек: NestJS/TypeScript/PostgreSQL/Prisma/Redis). Выполни шаги строго по порядку. Не пропускай шаг 1 — без контекста прошлых сессий работать нельзя.

## Шаг 1 — Загрузить контекст (обязательно)
1. Прочитай `TZ_CRM_Omuz_FINAL.md` — исходное ТЗ (источник истины по требованиям).
2. Прочитай `ROADMAP.md` целиком — фазы и статусы чекбоксов.
3. Прочитай **все** файлы из `sessions/` в порядке возрастания имени (`0000-…`, `0001-…`, …). Начни с `sessions/README.md`. Это память проекта: что уже сделано, какие решения приняты, где остановились.
4. Кратко (5–8 строк) отчитайся пользователю: на какой мы фазе, что было в последней сессии, какой пункт берём следующим.

## Шаг 2 — Определить следующую задачу
- Если пользователь передал аргумент `$ARGUMENTS` — сфокусируйся на указанной фазе/задаче.
- Иначе возьми **первый незакрытый** пункт (`[ ]` или `[~]`) в `ROADMAP.md`, идя по фазам сверху вниз. Не перескакивай через незакрытые зависимости.
- Бери реалистичный объём на одну сессию (один связный кусок функциональности, а не всю фазу разом, если она большая).

## Шаг 3 — Реализовать
- Пиши код в согласии с ТЗ и уже принятыми в прошлых сессиях решениями (стиль, структура модулей, конвенции API `/api/v1`, формат ответа `{ data, meta }` / ошибок `{ error }`).
- Держи границы модулей NestJS чёткими: `Controller → Service → Repository (Prisma)`.
- Для новых сущностей — обновляй Prisma-схему и создавай миграцию.
- Соблюдай сквозные требования ТЗ: RBAC-guard на защищённых эндпоинтах, валидация DTO, argon2id, пагинация списков.

## Шаг 4 — Проверить
- По возможности проверь сделанное: собери проект (`build`/`tsc`), прогони относящиеся тесты, применённую миграцию, вызов эндпоинта. Если полноценно проверить нельзя — честно отметь это в логе сессии.

## Шаг 5 — Записать лог сессии
- Определи следующий свободный номер `NNNN` (на 1 больше последнего файла в `sessions/`).
- Скопируй `sessions/SESSION_TEMPLATE.md` в `sessions/NNNN-краткое-описание.md` и заполни честно: цель, что сделано, решения, проверка, что не доделано, следующий шаг.

## Шаг 6 — Обновить roadmap
- Проставь `[x]` для полностью выполненных пунктов, `[~]` для начатых-но-незавершённых.
- Обнови строку «Общий прогресс» вверху `ROADMAP.md`.

## Шаг 7 — Закоммитить и запушить на GitHub
1. Убедись, что есть удалённый репозиторий: `git remote -v`. Если `origin` отсутствует — создай публичный репозиторий и привяжи (`gh repo create <имя> --public --source=. --remote=origin`).
2. Проверь, что репозиторий **публичный**: `gh repo view --json visibility -q .visibility`. Если `PRIVATE` — сделай публичным: `gh repo edit --visibility public --accept-visibility-change-consequences`.
3. `git add -A`, затем коммит с осмысленным сообщением на русском, например: `Фаза N: <что сделано>` (в конце сообщения — строка `Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>`).
4. `git push` (при первом пуше ветки — `git push -u origin <ветка>`).
5. Впиши хеш/сообщение коммита в лог сессии (шаг 5) и сообщи пользователю ссылку на репозиторий.

## Правила
- Никогда не пропускай чтение `sessions/` и `ROADMAP.md` — это единственная память между сессиями.
- Не коммить секреты: секреты только в `.env` (в `.gitignore`), в репозиторий — `.env.example`.
- Если сомневаешься в требовании — сверься с ТЗ; если и там неоднозначно — задай пользователю короткий вопрос, а не выдумывай.
- Лучше сделать один пункт качественно и проверить, чем много и вслепую.
